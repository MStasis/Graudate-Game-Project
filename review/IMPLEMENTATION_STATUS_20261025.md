# 중간보고 준비: 현재 구현과 검증

2026-10-25 기준. 기존 3D 코드는 재사용하지 않았고 원본 HWP를 변경하지 않았다.

## 현재 실행 가능한 범위

`START_DEMO.cmd`로 Godot 기반 시제품을 실행한다. 퓨즈를 찾아 전력을 복구하고 출구로 탈출하는 작은 장면이며 재시작할 수 있다. 질문을 보내면 현재 아이템·전력 상태와 NPC 설정을 로컬 Ollama에 전달한다. 응답은 HTTP 스트리밍으로 표시하고 시간과 상태를 JSONL에 남긴다.

최종 시연 구성은 Godot 4.7.2, Ollama 0.40.11, Qwen2.5 1.5B Q4_K_M, RTX 5070이다. 생성 설정은 `game/npc_config.json`에 있고 현재 temperature 0.3, context 2048, 최대 생성 192, seed 42다. 기본 대화는 이전 턴의 이력을 누적하지 않는 단일 질문 방식이다.

## 실제 생성 결과

동일 질문: “지금 무엇을 해야 해?”

| 상태 | 실제 응답 원문 | 첫 대사 | 완료 |
|---|---|---:|---:|
| 퓨즈 획득 전 | 먼저 퓨즈를 찾아야 합니다. 퓨즈는 B구역에 있습니다. | 0.067초 | 0.367초 |
| 퓨즈 획득 후 | 먼저 퓨즈를 장착해 전력 장치에 퓨즈를 달려야 합니다. 전력이 정지되어 있음을 확인하세요. | 0.067초 | 0.600초 |
| 전력 복구 후 | 현재 퓨즈를 사용하고 전력이 복구되었으므로, 출구로 나가보세요. | 0.067초 | 0.450초 |

위 결과는 최신 자동 시연 `run_id=12740`의 원문이며, 문장을 다듬지 않았다. 두 번째 문장에는 어색한 한국어 표현이 남아 있다. 안내 방향을 확인한 것과 문장 품질을 충분히 검증한 것은 구분한다.

로딩 이후·프롬프트 캐시 재사용 조건의 예비 3건이다. 첫 모델 로딩 요청은 첫 대사 약 15.683초, 완료 약 16.049초였다. 최초 실행과 이후 실행을 직접 비교해 모델 우위나 최적화 효과를 주장할 수 없다. 클라우드 API 비교와 대규모 시나리오 평가는 아직 하지 않았다.

## 검증 증거

- `evidence/npc_sessions.jsonl`: 초기 문제와 수정 후 실제 생성 기록 전체. 현재 모델과 `schema_version=2`, `run_id`를 구분해서 읽는다.
- `evidence/verified_demo_summary.json`: 최신 3상태 결과, 최초 모델 로딩 기록, 소스 SHA-256.
- `evidence/godot_evidence.log`: `DEMO_EVIDENCE_PASS requests=3 escaped=true`.
- `evidence/01_before_fuse.png`, `02_after_fuse.png`, `03_after_power.png`, `04_ending.png`: 실제 렌더링한 장면.
- `evidence/gameplay_test.json`: 전력의 퓨즈 선행 조건, 출구의 전력 선행 조건, 아이템 보유, 전력 복구 시 아이템 소비, 탈출, 재시작 초기화, 대사 생성 중 상태 보존 총 7개 통과.

최신 요청 세 건의 생성 중 처리 프레임 수는 22/36/27이며 벽시계 기준 최대 프레임 간격은 약 17.00/16.70/16.73ms였다. 이 제한된 자동 실행에서 프레임 처리가 이어진 결과이며 사람의 이동 입력 검증을 대신하지 않는다.

## 실제로 발견한 문제와 조치

1. Godot JSON의 포트 값을 그대로 문자열로 넣으면 `11434.0`이 되어 URL 해석에 실패했다. 정수로 변환해 수정했다.
2. 초기 Qwen3 4B 실행에서 추론 본문이 NPC 대사로 표시되고 생성 길이 제한에 걸렸다. API 대화 형식과 추론 필드 분리를 시험했고, 일부 응답은 분리했지만 다른 상태에서 길이를 초과했다.
3. 중간보고 시연의 안정성을 우선해 비추론 지시형 Qwen2.5 1.5B로 바꾸고 동일한 3상태를 다시 확인했다. 모델 교체는 비교 실험 완료를 뜻하지 않는다.
4. 원본 초기 화면과 로그는 `evidence/initial_thinking_issue/`와 전체 JSONL에 남겼다. 초기 로그의 `success=true`는 응답 전송 처리 성공이며 정상 대사 품질을 의미하지 않는다.
5. UI 하단 설명이 잘리는 문제를 간격 조정으로 수정하고 화면을 다시 확인했다.

## 발표자료

- `deliverables/졸업논문_중간보고_20261027.pptx`: 5장, 계획 대비 현재 진척·문제와 해결·실제 응답·향후 계획. 발표자 노트 포함.
- `deliverables/발표_연습용_메모.md`: 슬라이드별 발표 연습용 메모.
- 슬라이드 5장 모두 렌더링해 텍스트와 배치를 확인했다. PPTX ZIP/XML, 슬라이드 5개, 노트 5개, 편집 가능한 표 2개를 확인했다. 실제 PowerPoint 앱에서 열어본 검증은 하지 않았다.

## 사용자가 먼저 확인할 일

1. 시제품에서 같은 질문을 세 상태에 직접 보내고 답변 변화를 확인한다.
2. 방향키와 E로 퓨즈·전력 장치·출구를 직접 조작해본다.
3. PPT와 메모를 읽고 설명하기 어려운 문장을 자신의 말로 바꾼다.
4. 발표 전에 같은 PC에서 한 번 질문해 모델을 로딩하고, PPT가 발표 환경에서 열리는지 확인한다.

클라우드 API 비교, 한국어 표현 개선, 다양한 질문·오류 조건, 장기 대화, 논문 본문, 독립 실행 파일 배포, 다른 PC와 완전 오프라인 실행은 후속 작업이다. 외형과 콘텐츠도 최종 작품 수준의 제작을 마친 상태는 아니다.
