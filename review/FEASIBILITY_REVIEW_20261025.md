# 졸업작품·논문 일정 검토

검토일: 2026-10-25. 기준 자료: 사용자가 제공한 `1.2026학년도_졸업논문연구계획서_및_졸업논문발표계획서 (2).hwp`의 연구계획서와 발표계획서 본문.

## 판단

**11월 15일까지 작은 2D 게임, 로컬 AI NPC, 소규모 비교 실험, 논문과 수정 결과를 준비하는 목표는 조건부로 현실적이다.** 사용자가 확인한 졸업작품 공식 마감은 11월 18일이며, 16일 이전 완료를 원하므로 실제 완료 목표를 11월 15일 일요일로 잡는다. 일반적인 RPG 규모의 콘텐츠나 독자적인 모델 학습까지 포함하면 현재 일정에 맞추기 어렵다.

사용자 후속 답변을 반영해 **기존 3D 코드는 재사용하지 않고 처음부터 제작**, **월·금은 작업 시간 0시간으로 예산 편성**, **화·수·목·토·일은 각 7시간 확보를 목표**로 일정을 수정했다. 주당 계획 시간은 35시간이다. 엔진은 Godot 4 안정 버전 일반판과 GDScript를 추천하며, 새 엔진의 필요한 기초를 익히는 시간도 포함한다. 중간발표와 작품 마감은 사용자 답변으로 확인했다. 논문 자체의 공식 제출일·분량·양식은 별도 확인 사항이다. 통과 또는 완성 시점을 보장하는 판단은 아니다.

## 후속 구현 상태: 2026-10-25

사용자가 중간보고 준비를 위한 시작을 요청한 뒤 다음 결과를 실제로 확보했다.

- 동일 질문의 퓨즈 획득 전·후, 전력 복구 후 응답과 JSONL·화면 기록.

초기 Qwen3 4B 시험에서 추론 본문 노출과 생성 길이 제한을 확인했다. 추론 필드 분리 시험을 거친 뒤 시연 모델을 비추론 지시형 모델로 바꿨다. 실패 기록은 남겼다. 최신 시연 3건은 모델 로딩 이후와 캐시 재사용 조건에서 완료 약 0.37~0.60초였으며, 첫 모델 로딩 요청은 약 16.05초였다. 소수의 예비 시연으로 일반 성능을 보장하지 않는다.

현재 기록은 `evidence/verified_demo_summary.json`, 구현·검증 설명은 `review/IMPLEMENTATION_STATUS_20261025.md`, 실행 안내는 `README.md`에 있다. 클라우드 API 비교, 논문 본문 작성, 사람의 키보드 플레이, 독립 실행 파일·다른 PC·완전 오프라인 실행 검증은 남아 있다.

## 확인한 사실과 확인하지 못한 사항

- 원문 제목은 **「로컬 AI기반 게임 NPC 개발」**이다. 3D 제작은 필수 항목으로 명시되어 있지 않다.
- 연구계획서는 게임 상황과 플레이어 상태에 맞는 대사 생성, 로컬 경량 언어 모델 활용, 네트워크 의존과 유료 추론 API 호출 비용 문제 해결을 목표로 한다.
- 발표계획서는 **양자화·비동기 스트리밍**, 게임 프로토타입 내 구동, **클라우드 LLM API 대비 속도·답변 성능·메모리 분석**을 포함한다. 따라서 게임 화면만 완성하면 계획서의 전체 범위를 충족했다고 보기 어렵다.
- 현재 `Graduate_Project` 폴더에는 검토 시작 시 기존 프로젝트 파일이 없었다. 이후 사용자가 기존 3D 게임 코드는 있지만 이번 작품은 처음부터 제작하는 기준으로 검토해 달라고 확인했다. 기존 코드를 읽거나 변경하지 않았다.
- 사용자가 월·금에는 충분한 시간을 내기 어렵고, 화·수·목·주말에는 하루 약 7시간을 확보해볼 수 있다고 설명했다. 이는 확보를 목표로 한 시간이므로 전부 순수 개발 시간으로 실현된다고 보장할 수 없다.
- `nvidia-smi`에서 현재 PC의 RTX 5070, VRAM 12,227 MiB가 확인됐다. CPU와 시스템 RAM은 조회 환경의 제한으로 확인되지 않았다. 이후 Qwen2.5 1.5B 모델을 설치하고 게임에서 3가지 상태별 실제 대사를 확인했다. 최초 로딩과 이후 요청을 구분해 기록했으며, 한국어 자연스러움은 추가 개선이 필요하다.
- 중간발표는 **10월 27일 화요일 오후 1시, 약 5분의 PPT 발표**이며 중간고사를 겸한다. 평가에 드러나야 하는 내용은 계획 대비 진행 상황, 진행 중 문제, 해결을 위한 노력과 방안, 향후 진행 계획이다.
- 졸업작품 공식 최종 마감은 **11월 18일 수요일**이다. 사용자는 **11월 16일 이전** 완료를 원한다. 따라서 자체 완료일은 **11월 15일 일요일**로 잡는다. 이 작품 마감이 논문 마감과 동일한지는 확인하지 않았다.

## 계획서와 2D 전환의 관계

2D로 바꾸더라도 ‘게임 상태를 입력받아 로컬 모델이 NPC 대사를 생성한다’는 연구 목표는 유지할 수 있다. 그래픽보다 상태 전달, 비동기 실행, 측정 가능한 결과가 연구의 중심이다.

단, 문서에는 계획 변경에 관해 지도교수 사전 승인을 받는다는 문구가 있다. 이는 제출 문서에 적힌 절차를 검토한 것이며, 이 검토 작업 자체를 중단하거나 승인을 요구한다는 뜻은 아니다. 중간보고 때 2D 전환과 축소 범위, 비교 실험 계획을 함께 제시하고 허용 여부를 확인하는 편이 좋다.

## 권장하는 최종 작품의 크기

**장르 제안: 5~10분 분량의 2D 탐색·대화 어드벤처.**

예를 들어, 작은 연구소에서 부품을 찾아 전력을 복구하고 탈출하는 게임으로 구성한다. NPC 한 명이 플레이어의 부품 보유 여부, 전력 복구 여부, 부상 상태를 전달받아 다른 안내를 한다. 시작 안내 → 탐색·수집 → 상황에 맞는 NPC 대화 → 목표 달성 → 엔딩·재시작까지 연결하면 짧아도 완결된 게임으로 제시할 수 있다.

| 영역 | 최종 제출에 포함 | 이후 여유가 생겨도 우선순위가 낮은 항목 |
|---|---|---|
| 공간·등장인물 | 작은 맵 1개, AI NPC 1명 | 여러 지역, 다수 NPC의 자율 생활 |
| 게임 진행 | 목표 1개, 상호작용 물체 2~3개, 엔딩 1개, 재시작 | 전투 성장, 제작, 복잡한 인벤토리, 다중 엔딩 |
| AI | 검증한 로컬 모델 1개, 짧은 대화, 게임 상태 3종 반영 | 파인튜닝, 자체 모델 학습, 무제한 장기 기억 |
| 통신 | 비동기 요청, 실제 응답 스트리밍, 실패·시간초과 안내 | 음성인식·음성합성, 동시 다중 대화 |
| 비교·기록 | 클라우드 API 1종과 같은 상황으로 비교, 원본 로그 | 다수 모델의 대규모 벤치마크 |
| 전달물 | 실행 파일, 구동 설명, 실험 결과, 논문, 시연 영상 | 배포 플랫폼 출시, 다른 OS 지원 |

에셋은 최소한의 캐릭터·타일·상호작용 아이콘으로 통일한다. 새 엔진 학습, 에셋 탐색, 화풍 변경을 동시에 진행하지 않는 것이 중요하다.

## 엔진 추천: Godot 4 일반판 + GDScript

이번처럼 작은 2D 게임을 새로 만들고 로컬 AI와 실험 기록을 연결하는 조건에서는 Godot를 우선 추천한다. 후속 작업에서 포터블 Godot 실행 환경과 작은 2D 시제품을 준비하고 실제 로컬 AI 연동을 확인했다. 현재 실행 파일은 Godot 프로젝트를 실행하는 방식이며 독립 배포 패키지는 아직 준비하지 않았다.

- 2D 전용 렌더링·물리, 타일맵, 스프라이트 애니메이션, UI 편집 기능이 있다. [2D 공식 소개](https://docs.godotengine.org/en/stable/tutorials/2d/introduction_to_2d.html)
- 일반판을 압축 해제해 실행할 수 있다. 2026-10-25 공식 Windows 다운로드 페이지에서 4.7.2가 확인됐다. 시작할 때 안정 버전과 같은 버전의 export templates를 준비하고 제출까지 버전을 고정하는 것을 권장한다. [Windows 다운로드](https://godotengine.org/download/windows/)
- GDScript는 엔진에 통합되어 있고 공식 입문 문서에서도 처음 시작할 때 추천한다. 이번 규모에서는 외부 SDK 설정이 필요한 C# 대신 일반판+GDScript를 기본 제안한다. 사용자의 C# 숙련도는 확인하지 않았다. [언어 선택 문서](https://docs.godotengine.org/en/stable/getting_started/step_by_step/scripting_languages.html)
- HTTP 통신으로 로컬 추론 서버에 연결할 수 있다. 첫 연동은 HTTPRequest로 짧은 완성 응답을 확인하고, 최종 스트리밍은 HTTPClient의 비동기 폴링과 수신 바이트 누적·줄 단위 파싱으로 구현하는 경로를 제안한다. 임의의 수신 청크 하나가 JSON 한 줄 전체라고 가정하지 않는다. 한국어 UTF-8 바이트도 경계에서 잘리지 않게 처리해야 한다. 현재 시제품에 HTTPClient 기반의 비동기 스트리밍과 UTF-8 바이트 누적·줄 단위 파싱을 구현했다. [HTTPClient 클래스](https://docs.godotengine.org/en/stable/classes/class_httpclient.html)
- Windows 실행 파일로 내보낼 수 있다. 게임 실행 파일과 로컬 AI 런타임·모델 배포는 별개의 준비 항목이며, 게임을 export했다고 AI까지 자동 포함되는 것은 아니다. [Windows 내보내기](https://docs.godotengine.org/en/stable/tutorials/export/exporting_for_windows.html)

장르는 기존 제안인 5~10분 탐색·대화 게임을 유지한다. 2D 액션의 전투 감각이나 대규모 RPG 콘텐츠보다 상태에 따른 NPC 답변을 보여주기 쉽다는 것이 이번 선택의 이유다.

## 구현에서 지켜야 할 경계

게임이 체력·아이템·퀘스트 상태를 관리하고, NPC 모델에는 그 상태를 읽기용으로 전달한다. 모델은 대사와 안내를 생성하고, 아이템 지급·클리어 판정은 게임 규칙으로 처리한다. 이렇게 하면 모델의 잘못된 답변이 진행 자체를 망가뜨리는 문제를 줄일 수 있다.

가장 작은 구조는 다음과 같다.

`게임 상태 → NPC 설정·현재 상태·짧은 대화 이력 구성 → 로컬 추론 서버 → 대화창`

비교 실험에서는 같은 입력을 클라우드 API에도 보낸다. 로컬 HTTP API와 외부 클라우드 API를 문서에서 구분해 표기한다. 로컬 HTTP 통신을 사용한다는 사실 자체가 인터넷 의존을 의미하지는 않는다.

Ollama는 로컬 서버 API, 부분 응답 스트리밍, 생성 시간 관련 지표를 제공하므로 후보가 될 수 있다. 설치와 모델 다운로드를 마친 뒤 실제 오프라인 실행을 별도로 확인해야 한다. 후속 구현에서 도구·모델 다운로드와 실제 생성 확인을 수행했다. 인터넷 연결을 끈 상태의 실행은 아직 별도로 검증하지 않았다.

- [Ollama API 개요](https://docs.ollama.com/api/introduction)
- [Ollama 스트리밍 문서](https://docs.ollama.com/api/streaming)
- [Ollama 사용량·시간 지표](https://docs.ollama.com/api/usage)
- [Godot HTTPRequest 문서](https://docs.godotengine.org/en/stable/classes/class_httprequest.html)

## 중간보고까지 이틀의 목표

개발 목표는 **게임 상태가 실제 로컬 모델의 NPC 답변에 반영되는 경로를 증명하는 것**이다. 발표 준비의 필수 목표는 사용자가 전달한 네 가지 평가 항목을 5분 안에 증거와 함께 설명하는 것이다. 개발 진척이 부족해도 발표자료 제작 시간을 먼저 확보해야 한다.

10월 25일은 일요일이고 다음 날인 26일은 사용자의 가용 시간이 부족한 월요일이다. 따라서 ‘이틀’ 전체를 14시간 작업일로 계산하면 안 된다. 발표는 27일 오후 1시이므로 화요일의 7시간을 전부 발표 준비에 사용할 수도 없다. 발표 당일 오전의 가용 시간은 확인되지 않았으므로 그때 핵심 구현을 마무리한다는 일정은 잡지 않는다.

1. 10/25: 확보할 수 있는 시간 중 **마지막 2시간은 PPT용 내용·증거 정리와 발표 연습에 예약**한다. 그 앞의 시간에 작은 로컬 모델의 한국어 응답 확인 → Godot 대화 UI 연결 → 아이템 보유 상태 변경에 따른 답변 확인 순으로 시도한다. 시간이 부족하면 상태 반영 장면은 다음 단계로 남기고 실제 동작한 수준만 보고한다. 이동·맵 꾸미기보다 이 경로를 우선한다.
2. 10/26: 핵심 개발을 배정하지 않는다. 여유가 생겼을 때만 이미 확보한 자료를 확인한다.
3. 10/27: 오후 1시에 PPT로 발표한다. 당일 오전은 가능할 때만 파일 열기·글꼴·영상·발표 시간 확인에 사용하고 핵심 개발을 배정하지 않는다.
4. 보고 자료: 원래 목표, 2D 전환 이유, 실제 구현된 부분, 확인된 문제, 최종 범위, 비교 실험 일정. 구현 예정 기능과 작동 확인 기능을 구분한다.

시연 예시는 ‘부품이 없을 때 도움 요청 → 부품 획득 → 같은 NPC에 다시 질문 → 현재 상태를 반영한 답변’이면 충분하다. 로컬 추론이 실패했다면 규칙 대사나 녹화물을 실시간 AI 생성처럼 제시하지 않는다.

5분 발표에서는 긴 실시간 시연을 필수로 잡지 않는다. 실제 구현이 확보되면 스크린샷이나 10~20초 내외의 녹화 장면을 PPT에 넣고, 실시간 시연은 별도 질문이 있을 때 가능한 수준으로 준비한다. 녹화 화면에는 녹화임을 표시한다. 구현이 없으면 구조도와 작업 계획을 제시하되 실행 결과처럼 표현하지 않는다.

구성안은 `MIDTERM_PRESENTATION_OUTLINE_20261027.md`에 별도로 정리했다. 발표 슬라이드는 5장, 발표 내용 4분 40초와 전환·시간 여유 20초를 기준으로 한다.

## 최소 비교 실험 설계

예비 실험으로 입력과 평가 기준을 먼저 고정한다. 한 가지 출발점은 ‘상황·질문 20개 × 조건별 3회 × 로컬/클라우드 2종 = 120개 응답’이다. 이는 제한된 시나리오의 탐색적 평가 규모이며, 모든 게임 상황의 품질이나 통계적 우위를 보장하지 않는다.

| 항목 | 기록 방법과 해석 |
|---|---|
| 응답 지연 | 게임 클라이언트에서 요청 시작→첫 실제 대사 표시, 요청 시작→답변 완료를 각각 측정. 평균과 중앙값, 느린 사례를 함께 제시 |
| 게임 작동 | 생성 중 이동·입력 유지 여부, 프레임 시간 또는 FPS, 시간초과·실패 횟수 |
| 상태 반영 | 보유하지 않은 아이템을 보유했다고 말하는지 등 정답 조건으로 판정 |
| 대사 품질 | 설정 모순·무관한 답변·한국어 표현 문제를 정해진 기준으로 분류. 작성자 평가라면 그 사실과 한계를 명시 |
| 자원 | 동일 PC에서 게임+로컬 추론의 RAM·VRAM과 기준 상태를 기록. 클라우드 서버 내부 메모리는 관측할 수 없으므로 비교 수치로 만들지 않음 |
| 재현 조건 | 모델·양자화·프롬프트·출력 길이 제한·대화 이력·소프트웨어 버전·사양·측정 시점 기록 |

모델 로딩을 포함한 최초 실행과 로딩 이후 실행을 나누고, 비교 순서와 대화 이력을 통제한다. 서로 다른 모델·하드웨어의 비교라면 ‘이번 구성에서의 시스템 비교’로 해석하고, 차이를 전부 로컬/클라우드 방식 탓으로 돌리지 않는다. 제공자별 토크나이저가 다를 수 있어 토큰/초만으로 품질과 체감 속도를 판단하지 않는다.

시간이 확보되면 로컬 모델에 상태를 넣은 경우와 넣지 않은 경우를 추가 비교하면 상태 전달 구현의 효과를 설명하기 좋다. 다만 원래 약속한 클라우드 비교를 이 실험으로 임의 대체하지 않는다. API 이용이 불가능하면 지도교수와 평가 범위 변경을 협의한다.

## 논문에서 고쳐야 할 주장

- ‘로컬이 API보다 빠르다’는 결론을 먼저 정하지 않는다. 현재 구성에서 지연·품질·자원 사용의 교환 관계를 측정하는 연구로 작성한다.
- 비동기는 게임 화면의 정지를 줄이는 방법이고, 스트리밍은 첫 내용 표시를 앞당길 수 있는 방법이다. 둘 다 추론 연산 자체가 빨라졌다는 증거는 아니다.
- ‘일반적인 PC에서 응답속도 저하 없이’는 아직 입증되지 않았다. RTX 5070 한 대의 실험으로 모든 보급형 PC에 일반화하지 않는다.
- 제거 가능한 것은 외부 유료 추론 API 호출 요금과 실행 중 외부 네트워크 의존이다. 하드웨어·전력 등 모든 비용이 사라지는 것은 아니다.
- 사용자 평가 없이 몰입감 향상을 실증했다고 쓰지 않는다. 상태 반영 정확도와 실행 성능을 우선 검증한다.
- 기존 양자화 모델 활용과 독자적인 양자화 기법 개발을 구분한다. 학습 파이프라인 대신 상태·프롬프트·실험 로그를 처리하는 파이프라인으로 범위를 구체화할 수 있는지 확인한다.

관련 연구의 출발점으로 [Park 등의 Generative Agents 논문](https://arxiv.org/abs/2304.03442)을 검토할 수 있다. 이 연구의 기억·계획·반성·다중 에이전트 전체를 재현하겠다는 범위로 확장할 필요는 없다. 계획서에 기재된 도서 외에 NPC 관련 연구, 선택한 모델의 원문·라이선스, 추론 도구 문서를 실제 읽은 범위로 보강한다.

논문 구조는 ‘문제와 목표 → 관련 연구 → 시스템 설계 → 구현 → 실험 방법·결과 → 한계·결론’으로 잡을 수 있다. 기여는 새로운 언어 모델 개발이 아니라 게임 상태 연동, 실행을 막지 않는 대화 처리, 측정한 적용 조건과 한계로 구체화한다.

## 일정이 밀릴 때의 판단 기준

- 첫날 로컬 모델이 동작하지 않으면 모델 규모·실행 환경부터 조정한다. 자체 학습으로 해결하려 하지 않는다.
- 중간보고 전 상태 반영 대화가 연결되지 않으면 맵 꾸미기와 추가 NPC 작업을 멈추고 연동에 집중한다.
- 일주일 안에 엔딩까지 연결되지 않으면 장소·목표·상호작용을 줄인다.
- 11월 8일까지 게임 기능 추가를 종료하고, 이후에는 논문·오류 수정·패키지·제출물을 우선한다.

제출 전 별도 확인 사항: 논문 자체의 공식 제출일·양식·분량, Godot 학습에 드는 실제 시간, 클라우드 비교에 쓸 계정·예산, 발표 PC의 로컬 모델 구동 가능 여부. 중간발표는 10/27 13:00 약 5분 PPT, 작품 마감은 11/18, 자체 목표는 11/15로 반영했다. 기존 3D 코드 재사용 여부와 요일별 가용 시간도 사용자 답변으로 확인했다. 원문 연구계획서의 제출 연도는 2024, 발표계획서는 2026으로 적혀 있어 서식 재사용 시 날짜도 확인한다.
