# NPC 비교 실험 프로토콜 초안

상태: 실험 설계 초안. 본 실험 데이터 수집은 아직 시작하지 않았다.
2026-10-25의 provider_probe와 통합 검사는 개발용이며, 결과 우열을 보고하는 본 평가 표본과 분리한다.

## 평가를 두 축으로 나누기

A. **지원 행동 비교**: 같은 관측 상태, 같은 유효 행동 목록과 설명, 같은 지원 실행기, 같은 적/자원/피해 조건.
세 방식의 다음 행동 선택·지연·실행 결과를 비교한다.

B. **대화 시스템 비교**: 같은 현재 목표, 사실, 동료 관계와 질문을 제시한다.
규칙 기반과 Jev는 의도+준비된 문장, 로컬 LLM은 자유 생성이다. 이 결과는 완성된 NPC 시스템 비교로 해석하며 순수 모델의 동일한 텍스트 생성 능력 비교로 주장하지 않는다.

## 조건 고정

- 코드의 project_fingerprint, 프롬프트 버전, 시나리오 버전 기록.
- 엔진/Ollama 버전, 실제 모델 식별자와 양자화, 생성 옵션, 문맥 길이, 최대 토큰, thinking 여부 기록.
- GPU/CPU/RAM, 화면 크기, 렌더러, 전원/백그라운드 부하와 실험 실행 방식 기록.
- 적 위치·체력·이동·공격, 플레이어 체력·탄약·무기, 하린의 지원 자원·효과·쿨다운·접근 조건을 동일하게 유지.
- 현재 적 배치는 고정이며 난수 행동을 사용하지 않는다. seed=42는 현 시나리오 식별 설정이고 무작위성을 실제 제어한 실험 결과로 과장하지 않는다.
- 행동 요청 기본 간격 1.5초, 기본 결과 유효 시간 3초. 로컬/외부 요청의 타임아웃과 호출 상한을 함께 명시.
- 후보의 형식/유효성 검사는 모두 적용한다. 현재 할 수 없는 행동을 실행기가 거절한 횟수도 결과에 포함.
- Jev는 외부 API 왕복 시간이 포함된다. localhost와 같은 네트워크 조건이라고 표현하지 않는다.
- 낮은 수준의 동행·접근·피해 판정은 공통이다. 모델은 지원 종류를 고른다.
- 기본 설정의 규칙 우선순위: 체력 55 이하 치료 → 탄약 4 이하 보급 → 전투 중 보호 장비 → 보호 지점 안내 → 동행. 유효 후보 조건을 먼저 적용한다.
- 상태 스냅샷에 다음 목표 안내를 공통 제공한다. 따라서 임무 추론 자체보다 제공된 상태/목표를 사용한 설명·판단을 평가하는 설계다.

실험 도중 프롬프트·장비·수치를 변경하면 조건 버전을 새로 만들고 데이터를 섞지 않는다.

## 고정 상태 평가 초안

지원 상태 8종 × 각 5회 × 3방식 = 120건의 행동 요청을 계획한다.

1. 낮은 체력, 충분한 탄약, 사용 가능한 키트.
2. 정상 체력, 탄약 없음, 보급품 있음.
3. 체력과 탄약 모두 부족.
4. 즉시 치료/보급이 불필요하고 적이 접근하는 상황.
5. 보호 장비가 설치되었고 플레이어가 밖에 있는 상황.
6. 플레이어가 이미 보호 구역 안에 있는 상황.
7. 지원이 필요하지만 자원이 고갈된 상황.
8. 전투가 없고 체력/탄약이 충분한 상황.

각 상태를 보며 허용할 만한 행동의 집합과 금지 행동을 **출력 확인 전에** 정한다.
복수의 합리적 선택이 있는 상태는 하나의 답만 정답으로 고정하지 않는다.
현재 개발 probe의 expected_actions는 초기 참고 우선순위일 뿐, 독립 검증된 정답 데이터셋이 아니다.

대화 질문 6종 × 각 3회 × 3방식 = 54건의 질문을 계획한다.

- 출발 전 다음 목표
- 전투 중 도움 요청
- 퓨즈 회수 뒤 다음 행동
- 친한 동료 관계 확인
- 안부·감정에 관한 일상 대화
- 주어진 사실에 없는 과거/장소 질문

현재 개발에 사용한 정확한 질문을 그대로 본 평가의 유일한 질문으로 쓰지 않는다.
바꿔 말한 질문과 미리 보지 않은 상태 조합을 포함하고, 모델 답변을 보고 정답 문장을 수정하지 않는다.
가능하면 판정자 2명을 두고 불일치를 기록한다. 1명이 판정한다면 기준과 원문·한계를 공개한다.

계획상 Jev는 행동 40건 + 대화 18건 = 58건이며, 실행당 기본 호출 상한 60회와 구분해 관리한다.
실제 요청은 키/계정 준비 후 실행하며 재시도·실패도 호출 수와 비용에 포함한다.

## 지표

| 영역 | 지표 | 주의점 |
|---|---|---|
| 지연 | 전체 반환 시간, 대사 표시 준비 시간, 행동 효과 완료 시간 | 첫 JSON 토큰과 플레이어가 읽을 대사는 다름 |
| 실시간성 | 추론 대기 프레임 수, 최대 프레임 간격, 상태 변경 중 진행 | headless와 렌더링 실행을 섞어 비교하지 않음 |
| 행동 형식 | 후보에 포함되는 응답 비율, 파싱 실패 | 유효 형식이 적절한 판단을 보장하지 않음 |
| 행동 적절성 | 사전 허용 집합과 일치, 낭비·지원 실패·지연 도착 | 실행기의 보호 기능으로 감춰진 모델 오류도 기록 |
| 실행 결과 | 실제 체력/탄약 변화, 보호 피해 감소, 임무 성공·소요시간 | 같은 플레이어 입력 또는 같은 상태 흐름으로 비교 |
| 대화 | 임무 정확성, 상태/관계 일관성, 질문 관련성, 자연스러움 | 근거 없는 과거, 다국어 혼입, 일상 질문에서 임무 반복 별도 표시 |
| 실패 | 인증/시간초과/HTTP 오류, stale_epoch/age, 유효성 거절 | 실패 표본을 지연 표에서 조용히 삭제하지 않음 |
| 자원 | RAM/VRAM, CPU/GPU 부하, 외부 호출 수/사용량/비용 | 자동 자원 계측은 아직 추가하지 않음 |

각 조건에서 표본 수, 실패/거절 수와 비율을 먼저 제시한다. 지연은 중앙값·평균·p95와 측정 조건을 병기한다.
소수 반복의 p95는 불안정하므로 실제 개별 값도 보관한다. 현재 몇 건의 요청으로 p95나 통계적 유의성을 주장하지 않는다.

모델 적재가 필요한 첫 요청과 준비된 뒤의 요청을 분리한다.
독립 반복에서 모델을 실제로 내렸는지 확인하지 않은 경우 'cold'라고 부르지 않는다.
현재 개발 점검의 첫 요청은 엄밀한 cold 조건으로 통제하지 않았다.

## 실제 플레이 평가를 추가한다면

세 방식의 순서를 사람마다 바꾼다. 예: ABC/BCA/CAB 등으로 순서 효과를 분산한다.
튜토리얼, 시작 자원, 적 배치와 질문 기회를 동일하게 유지하고 각 방식 사이에 회차 기억을 초기화한다.
자연스러움·도움 정도·믿을 만함·기다림 불편에 대한 동일한 짧은 질문을 사용한다.
소수 사용자 결과는 탐색적 결과로 명시한다. 현재 사람 플레이 평가는 수행하지 않았다.

## 로그 사용

활성 로그는 evidence/mission_v1 이하이다. 이전 evidence/scene_refactor 자료와 합치지 않는다.

- npc_events.jsonl: schema_version=4. provider, run_id, trial, scenario_id, project_fingerprint, prompt_version, run_kind를 이용해 조건 분리.
- response: snapshot, snapshot_hash, allowed, selected, accepted, rejected_reason, elapsed_ms, snapshot_msec, response_msec.
- LocalLLM: actual_model, raw_response, first_transport_text_ms, server_metrics, dialogue_method.
- Jev 실호출 성공 시: actual_model, probabilities, confidence, usage.
- world_event/details: support_started / support_completed / support_rejected, 자원/효과, 요청 식별자.
- request_failed: 오류와 걸린 시간. 오류가 없는 응답 행만으로 전체 성공률을 계산하지 않음.
- raw npc_sessions.jsonl: 로컬 system/prompt, 스키마, thinking, 생성 옵션, 응답 원문과 서버 지표.

실제 지원 효과의 지연은 같은 run_id / trial / provider / request_id로 지원 완료 이벤트를 연결해 산출한다.
기본 실행과 개발 검사 데이터는 synthetic_test, automated_evidence, run_kind로 나눈다.
판정의 수락 여부를 문장 품질 점수로 대체하지 않는다. 지침 위반이나 불필요한 지원도 원문에서 평가한다.

## 현재 실행 도구

- VERIFY_MISSION.cmd: 50개 기능 검사
- scripts/verify_mission.ps1 -Render: 규칙 기반 렌더링 임무
- scripts/verify_mission.ps1 -LocalAI: 현재 로컬 모델의 실제 지원 통합
- game/tests/provider_probe.gd: 개발용 고정 입력 점검 6건. 본 실험 전체 러너는 아직 아님.

Jev 키 없는 검사, 합성 API 응답, 규칙 기반 시연을 실제 Jev 성공 표본으로 집계하지 않는다.
최종 보고 전 Jev 실제 요청/응답, 정식 평가 코퍼스, 반복 수집기와 CPU/GPU 메모리 계측을 추가해야 한다.
